# 配方命名、发布仓库与幂等判定（2026-11-23）

本轮三件事：配方路径回到「上游 npm 名」，发布目标换成 `npm-rv-test-local` 并支持 HTTP Basic
凭据，以及修掉同名策略下会静默漏发的一个幂等判定 bug。

## 1. 路径：`packages/<npm 名>/<version>`

三个包在上游 npm 都是 **unscoped**（`bufferutil`、`utf-8-validate`、`rolldown`），所以按约定
移回一层：

```
packages/@ruyisdk/bufferutil/4.2.0      -> packages/bufferutil/4.2.0
packages/@ruyisdk/utf-8-validate/6.0.6  -> packages/utf-8-validate/6.0.6
packages/@ruyisdk/rolldown/1.3.3        -> packages/rolldown/1.3.3
```

* 路径是**配方身份**（= 上游包名），不承载「挂谁的 scope」；那条信息属于
  `npm_publish[].name`。
* scoped 包仍占两段（`packages/@scope/name/1.2.3`），`slugify` 规则不变。
* 需要 scope 时用 **`@ruyirepo`**（`--publish-scope ruyirepo` / 仓库变量 `PUBLISH_SCOPE`），
  不再用 `@ruyisdk`——那是上游组织的 scope，我们没有发布权。

## 2. 发布名沿用上游名（不加 scope）

`npm_publish[].name` 改成 `bufferutil` / `utf-8-validate` / `rolldown`。理由不是省事，而是**透明
替换**：`npm i rolldown` 只有在发布名与上游一致时才可能拿到 riscv64 版本（细节见第 4 节）。
若某天目标仓库强制要求 scope，改 `--publish-scope ruyirepo` 一行即可，配方不动。

## 3. 发布仓库 + Basic 凭据

目标：`https://forgestash-old.verify.oepkgs.net/repository/npm-rv-test-local`。
探测结果：`/-/ping` 200、包元数据 **401**，响应头带
`WWW-Authenticate: Basic realm="ForgeStash platform"` —— 要 HTTP Basic，不是 npm bearer token。

因此 `.stat` 新增字段：

```yaml
    registry: https://forgestash-old.verify.oepkgs.net/repository/npm-rv-test-local
    token_env: NODE_AUTH_TOKEN     # 环境变量名
    auth: basic                    # token（默认，写 _authToken）| basic（写 _auth）
```

生成器两处改动：

1. `setup_auth <registry> <token_env> <auth_kind>`：`basic` 写 `_auth`（值为 base64
   `user:password`），`token` 写 `_authToken`。
2. 授权行的 key 改成**完整 registry URL**（含路径，带尾斜杠）：`//host/repository/name/:_auth=...`。
   之前只写 `//host/`——对 `/repository/x/` 这种带路径的仓库，npm 是按它实际访问的 URL 查凭据的，
   写全路径最稳（无路径的仓库如 npmjs/GH Packages 结果与旧写法一致）。

凭据获取与注入：

```bash
printf '%s' 'user:password' | base64          # 目标平台账号的口令/API token 的 base64 形式
gh secret set NPM_PUBLISH_TOKEN --repo <owner>/npm-riscv64
```

工作流把 `secrets.NPM_PUBLISH_TOKEN` 映射成配方读的 `NODE_AUTH_TOKEN`；`token_env` 始终是
**环境变量名**（npm 惯例），这样换仓库不用改断码，也不用改 secret 名。

## 4. 幂等判定：从「先查后发」改成「发完看回答」

原实现：`npm view "$name@$version" version --registry "$registry"` 命中就跳过。**同名策略下这是伪
信号**：仓库只要接了 npmjs 上行/组仓库，`npm view bufferutil@4.2.0` 会读到**上游**的同名版本，
于是判定「已发布」并静默跳过——本轮 verdaccio 演练实锤：

```
[publish] package bufferutil@4.2.0 (dir=src/., manifest=generate)
[publish] already published: bufferutil@4.2.0 (skipped)     # ← 仓库里其实什么都没有
```

改成：**先发，再按目标注册中心的回答分类**：

* 成功 → `published <name>@<version>`；
* 409 / `EPUBLISHCONFLICT` / `already exists` / `previously published` / `cannot publish over`
  → `already published: ... (the registry refused a second publish; skipped)`，job 仍绿（重跑语义
  不变）；
* 其它错误 → 打印 registry 原文并失败。

判定权交回仓库本身：只有它知道「这个版本在不在我这里」。

## 6. 两条给消费者的前提（写进 README）

1. `npm-rv-test-local` 是 hosted 仓库，里面只有我们发进去的包；直接指向它，普通依赖全是 404。
   正确姿势：把它与 npmjs 代理组成 group/虚拟仓库，或在消费者 `.npmrc` 里按 scope 分流。
2. 同名同版本：组仓库里 hosted 优先，消费者拿到 riscv64 版；但 upstream 已经走到更高版本时，
   `latest` 会解析到上游那个没有 riscv64 绑定的包。也就是说「透明替换」覆盖我们发布过的那些版本。
   另外重发同版本会被仓库拒（脚本按「已发布」跳过，不会失败）。

## 7. 途中踩的坑（记一下，别再踩）

* 原生 `mask` 是 **5 参数**（`source, mask, dest, offset, length`）、`unmask` 是 **2 参数**
  （就地还原）。我用 2 参数调 `mask` 做自测 → 触发上游 `assert(status == napi_ok)` 崩溃，一度
  误判「产物坏了」。真相是调用方错，产物与仓库自身测试一致（sha256 相同）。
* verdaccio 在本机没配 npmjs 上行，消费者装 `bufferutil` 时因缺 `node-gyp-build` 报 404——顺手把
  `node-gyp-build`、`@oxc-project/types`、`@rolldown/pluginutils` 也镜像进 verdaccio 才能跑「纯本
  地仓库」场景。
## 8. 追加：CI 发布报 `ENEEDAUTH` 的真正原因（registry URL 少了结尾斜杠）

现象：secret 已配好，脚本日志也打出 `auth configured for //host/repository/npm-rv-test-local/ via
NODE_AUTH_TOKEN (basic)`，但 `npm publish` 直接 `npm error code ENEEDAUTH / need auth ...`，
且**注册中心一个请求都没收到**。

排查路径（用本地 mini registry 精确复现，见下）：

1. `_auth`（Basic）本身可用 —— 对 npm 9.2.0 / 10.9.11 / 11.21.3 逐个实测，凭据都能被解析，npm 发的确实是
   `Authorization: Basic ...`；
2. npm 的 `publish` 命令在真正发包**之前**做预检
   （`lib/commands/publish.js`：`getCredentialsByURI(registry)`，要有 `token` 或 `username`）；
3. `getCredentialsByURI` 用 `nerfDart(uri)` 取 key，而 `nerfDart` 的实现是
   `new URL(".", `${protocol}//${host}${pathname}`)` —— **把 registry URL 当文件名取父目录**：

   | registry URL | npm 实际去查的 key |
   | --- | --- |
   | `https://host/repository/npm-rv-test-local` | `//host/repository/` ← 最后一段被砍掉 |
   | `https://host/repository/npm-rv-test-local/` | `//host/repository/npm-rv-test-local/` |

   于是我们写的完整路径 key 永远匹配不上，`noCreds` 成立 → `ENEEDAUTH`，请求根本没发出。

修法：渲染器在生成发布脚本时把 registry URL **规范成以 `/` 结尾**（`normalize_registry`），
`setup_auth` 与 `publish_one --registry` 用同一个规范化值；`.stat` 里也补上结尾斜杠并加注释说明。
npmjs / GH Packages 这类没有路径的 registry 规范化后与旧行为完全一致（`//registry.npmjs.org/`）。

复现用的 mini registry（只认 Basic、挂在 `/repository/npm-rv-test-local` 路径前缀下）验证：

```
# 无斜杠 → npm 认为没凭据，不发包
npm ERR! code ENEEDAUTH
# 有斜杠 → 正常
PUT /repository/npm-rv-test-local/probe-path-auth auth=Basic accepted
+ probe-path-auth@1.0.0
```

L0 增加 `test_registry_url_is_normalized_to_a_directory` 与断言「发布参数里的 registry 带结尾斜杠」，
避免以后再退回去。

## 9. 追加：CI 里 rolldown "publish 卡住" 的定位与修复

用户报告 `rolldown` 发布一直不动。用目标仓库凭据直连实测：

| 动作 | 结果 |
|---|---|
| 10 MB 裸 PUT（无效体，只测上传通道） | `http=200 uploaded=10485760 time=85ms`（~120 MB/s） |
| 真实小包 `dsh-probe-slot@0.0.1` | `npm http fetch PUT 201 ... 199ms`，`+ dsh-probe-slot@0.0.1`，总 0.8s |
| 真实 `rolldown@1.3.3`（9.4 MB / 20.5 MB unpacked，59 文件） | `npm http fetch PUT 201 ... 865ms`，`+ rolldown@1.3.3`，总 4.2s |

结论：仓库、凭据、`auth: basic`、大包上传都没问题。**"卡住"是我们脚本造成的观感**——原实现
`out=$(npm publish ... 2>&1)` 把输出存进变量，命令结束前日志一片空白。已改为：

```bash
out_file="$(mktemp)"
set +e
npm publish "$abs_dir" --registry "$registry" --access public \
  --ignore-scripts --no-audit --no-fund --loglevel http 2>&1 | tee "$out_file"
status=${PIPESTATUS[0]}
```

即**流式输出 + `--loglevel http`**：慢上传会在 CI 日志里直接看到 `npm http fetch PUT ... <耗时>`，
而不再是静止画面；错误分类仍基于 `$out_file` 内容（409/EPUBLISHCONFLICT 等 → skip）。

配套修掉的两处：

1. 清理上一版遗留的一行重复 tail（`bash -n` 才发现，`unbound variable` 暴露的）；
2. 记录 `.stat` registry 必须带结尾斜杠（见 §8），否则 `ENEEDAUTH` 且不发请求。

消费者侧另一个坑（写进 README）：仅做 scope 分流还不够，npm 默认会把 npmjs 的
`dist.tarball` 改写回默认 registry（`replace-registry-host` 默认 `npmjs`），于是 metadata 200、
tarball 404。加 `replace-registry-host=never` 后实测通过：

```
added 3 packages in 15s
bundle ok, arch=riscv64
```

附注：仓库里现存 `bufferutil@4.2.0`、`utf-8-validate@6.0.6`、`rolldown@1.3.3`（均 unscoped），外加我
做计时探针时留下的 `dsh-probe-slot@0.0.1`——该仓库的 DELETE 接口返回 200 但实际不删，需要在界面上手动删掉。

## 10. 追加：组仓库验证与"全局 CLI 仍是上游副本"的坑

用户在 riscv64 上 `npm i rolldown --registry=…/npm-rv-test-group`（组仓库 = `npm-rv-test-local` +
npmjs，本地优先）成功 `added 3 packages in 8s`，但随后跑 `rolldown src/main.js --file bundle.js`
报 `Cannot find native binding`。堆栈路径说明一切：

```
at /usr/local/lib/node_modules/rolldown/dist/shared/binding-Bcod4zWj.mjs
```

那是**早前从 npmjs 全局安装的副本**；`rolldown` 命令走的就是它，而上游包里没有任何 riscv64 绑定
（`./rolldown-binding.linux-riscv64-gnu.node` → `@rolldown/binding-linux-riscv64-gnu` → wasm 的
fallback 链全是缺的，正是报错里的 cause 链）。而且用户那次 `npm i` 之后项目目录里并没有留下
`node_modules`（他自己的 `ls -R` 只有 `src/`），所以也没有本地副本可兜底。

验证（本机 riscv64 容器，组仓库）：

| 路径 | 结果 |
| --- | --- |
| 组仓库 tarball | 59 文件、9.4 MB，含 `dist/shared/rolldown-binding.linux-riscv64-gnu.node` ✓（确认组仓库本地优先给的是我们的包） |
| `npm i -g rolldown@1.3.3 --registry=<group>` | `added 3 packages in 22s`；`/usr/local/lib/node_modules/rolldown/dist/shared/*.node` 19.5 MB ✓ |
| 全局 CLI | `✔ rolldown v1.3.3 Finished in 637.35 ms`，bundle 正确 |
| 项目内 `npm i` + `npx rolldown` | 同样 ✓（`Finished in 613.70 ms`） |

结论：包与仓库都没问题，是消费者侧的"全局副本"问题。README 已补两条：
1. 组仓库方案（`--registry=<group>` 即本地优先 + npmjs 代理，无需 `.npmrc`、无 `replace-registry-host` 坑）；
2. 全局安装必须同样指向该仓库，并给出 `ls ... dist/shared/*.node` 的自检命令。

附注：用户日志里 `npm http fetch POST 200 …/-/security/advisories/bulk` 后跟
`audit error … invalid json`，是组仓库没实现 audit 端点，npm 当作非致命（exit 0），`--no-audit` 可静音。

## 11. 非 riscv64 客户端的实际行为（x64 实测）

问题：同名同版本发布后，x64/arm64 客户端能不能装、能不能跑？

回答：**能装能跑，但用的是上游自己的二进制/源码**——我们只是"加装"了 riscv64 产物，没有改
upstream 的 fallback 逻辑，也没有设 `os`/`cpu` 限制。x64 实测（宿主机 x64 + npm 9.2.0 + node 22）：

| 场景 | 结果 |
| --- | --- |
| 组仓库 `npm i rolldown` | `added 5 packages in 6s`（含 `@rolldown/binding-linux-x64-gnu`、`-musl`），`rolldown({input})` → bundle 成功 ✓（我们的 riscv64 `.node` 也在包里，但不被加载） |
| 组仓库 `npm i bufferutil utf-8-validate` | `added 3 packages`，无 x64 prebuild → `node-gyp-build` **现场编译**出 `build/Release/*.node`，`mask`/`utf8` 调用正常 ✓ |
| hosted-only 仓库 `npm i rolldown` | **失败** `404 @oxc-project/types`（普通依赖不在 hosted 里）→ 装都没装成 |
| hosted-only 仓库 `npm i bufferutil` | **失败** `404 node-gyp-build`（同上） |

结论与建议：
1. 我们的包**不是** riscv64-only；非 riscv64 客户端会走上游路线，前提是走**组仓库**（有 npmjs 代理）；
2. `bufferutil` / `utf-8-validate` 在非 riscv64 上是**源码编译**，需要 C/C++ 工具链（无工具链则 install 失败）；
3. 若确实希望只允许 riscv64 安装，可在 `.stat` 的 `npm_publish[]` 里写 `os: linux` + `cpu: riscv64`
   （渲染器已支持，写入 manifest 的 `os`/`cpu`，已实测 `publish_one … "linux" "riscv64"` 与
   `pkg.os = [osName]` / `pkg.cpu = [cpuName]` 生效），npm 会以 `EBADPLATFORM` 拒绝而非静默 fallback。
