## 2. 由 D22/D23 推出的三档优先级

publish 步骤的生成深度不再是一个布尔开关，而是三档：

```
① 配方提供 commands/publish        → 完全交给配方；generate_manifest 被忽略
② 无配方片段 + generate_manifest:true  → 生成发布步骤 + 在 publish 阶段生成/更新清单
③ 无配方片段 + generate_manifest:false → 生成发布步骤 + 只校验清单（缺失/不一致即失败）
```

这与 fetch / patch 的处理方式对齐，五步中「配方未提供则生成」的规则现在是统一的，不再有 publish 特例。

## 3. create / update 两种模式（由文件是否存在自动判定）

| 模式 | 触发 | 行为 |
|---|---|---|
| create | `dir` 下无 `package.json` | 用 `.stat` 生成最小清单（`name`/`version`/`main`/`os`/`cpu`） |
| update | 已有 `package.json` | 读入 → 只改 `version` 与 `optionalDependencies[requires[0]]` → 写回，**其余字段原样保留** |

不需要新增字段：文件在不在，就决定了走哪条路。

**这里有个必须防的坑（新增风险 R-i）**：update 若用 heredoc 整文件重写，会把 B 包原有的 `dependencies`、`exports`、`files`、`scripts` 全清掉 —— 发布出去的将是一个不可用的包，而且 npm 上无法可靠撤回。因此 update 必须是真正的 JSON 合并（`jq` / `node -e`），并在 S4 验收里比对「非目标字段发布前后一致」。

## 4. 一致性责任随档位转移（本轮最重要的语义变化）

| 校验项 | 档位 ②（生成） | 档位 ③（不生成） |
|---|---|---|
| A 清单 `name`/`version` 与 `.stat` 一致 | 写入即成立 | 必须断言 |
| A 的 `os`/`cpu` | 写入字段 | 必须断言 |
| B 的 `optionalDependencies[A.name] == A.version` | update 写入，天然成立 | 必须断言 |
| **产物架构是 RISC-V** | **仍必须断言** | **仍必须断言** |

上一轮我把「交叉校验」当成一律要做的动作；现在它只在档位③是必需项 —— 档位②里由写入保证了。但有一条例外必须保留（新增风险 R-k）：**「写入即成立」不等于「不用校验」**。清单是渲染器写的，`.node` 却是编译出来的；架构断言与档位无关，两档都得做，否则「清单写着 riscv64、产物实为 x86」这种最危险的错误会在档位②下静默通过。

## 5. 新发现的时序陷阱（R-j）

清单更新发生在 **publish 阶段**，而 test 在更早的步骤跑。测试时 B 的 `optionalDependencies` 还没指向本次构建的 A —— 如果配方在 `commands/test` 里写「装 B、看它能否加载二进制」，测到的其实是旧状态。

处理方式写进 §6.4：**需要验证 A/B 联动的 test 片段，必须自己把 A 目录链入**（`npm install ./<A.dir>`），不能指望 publish 阶段的清单更新。这类问题不会报错，只会让测试变成空转，属于最难发现的一类。
