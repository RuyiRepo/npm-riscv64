## 2. 需求方对我提出的疑点的裁定（要点）

**2.1 关于「版本目录是例外不是全集」的歧义 —— 需求方纠正我，我是错的。**
原判断基于「只有通用不满足才建版本目录」，据此推出文件系统读不出全集。需求方补充：`packages/<包名>/<版本>/.stat` **每个版本都会有**，所以**版本目录本身就是全集**，只是目录内不一定有 `patches/`、`commands/`。草案已按 D1-C 改写：

- 枚举 = `packages/<pkg>/` 下除 `common` 外的所有子目录
- `.stat` 是目录存在性的必要条件 → detect 阶段即可校验，不需要额外清单
- 副产物：我原提的「D1-A 版本清单」方案彻底删除，同时消除了「清单与实际目录不同步」这一类新隐患

**2.2 关于 npm 子集能否覆盖「从 registry 取已发布源码包」—— 能，但要补两处。**
答复已写入 plan §3.3：

1. 需通过 registry **元数据 API 解析 `dist.tarball`**，不能自行拼 URL（官方源以外、私有镜像、tarball 落在 CDN 的情况都会拼错）；scoped 名需 URL 编码（`@scope/name` → `@scope%2Fname`）。
2. 建议补 `npm.registry` 字段（默认官方源），这样镜像站也可覆盖。
3. **局限必须在文档里说清**：registry 上是发布产物，原生模块包常只含预编译 `.node` + JS 包装层，**可能根本没有可编译源码** —— 所以 npm 只能作最后兜底，且失败信息要提示这一原因。解包需 `--strip-components=1`（顶层是 `package/`）。

**2.3 关于 `fetch`/`patch` 的实现位置** —— 采纳「两种都支持」：默认按元数据自动生成，配方可用同名片段覆盖。这带来一条新规则：生成优先级 `片段（版本）> 片段（common）> 自动生成`。

## 3. 由 D2 措辞推出的一个新约束（需要留意）

D2 定的是「**同名文件整体替换**」。把这条规则一致地套到 `.stat` 上，会得出：若允许 `common/.stat`，则版本目录的 `.stat` 会**整体替换**它（而非字段级继承），common 的那份形同虚设。

因此草案加入 **Q1：暂不允许 `common/.stat`**，接受「上游 repo 地址在各版本重复写」的轻微冗余。这是为了让合并规则保持单一 —— 一旦引入「元数据字段级继承」，就会同时出现两套合并语义（文件级 + 字段级），配方作者难以预期。
