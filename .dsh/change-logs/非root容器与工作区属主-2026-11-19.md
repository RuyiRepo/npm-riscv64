# 非 root 容器与工作区属主（发布步骤 EACCES 修正）

日期：2026-11-19
触发：L3 第一次真正发布，`publish` 步骤报 `EACCES: permission denied, open 'src/package.json'`。

## 1. 现象

```
[publish] auth configured for npm.pkg.github.com via NODE_AUTH_TOKEN
[publish] package @cannedfish/bufferutil@4.2.0 (dir=src/., manifest=generate)
Error: EACCES: permission denied, open 'src/package.json'
```

注意失败点在**写 manifest**，还没走到 registry 交互。

## 2. 原因

`src/` 是容器（以 root 身份）拉下来并构建的，目录里每个文件都归 root 所有。而 GitHub
runner 上的步骤以 `runner` 用户执行，发布阶段要在 `src/package.json` 上做「生成/改名」，
于是写别人家的文件失败。

本地一直没暴露，因为本地 L1 也是以 root 跑宿主机步骤——属主一致，永远可写。

## 3. 改法

所有会写工作区的容器步骤统一带上：

```bash
--user "${RISCV_DOCKER_USER:-$(id -u):$(id -g)}" \
-e HOME=/w/.container-home -e npm_config_cache=/w/.container-home/.npm
```

- 工作区产物的属主 = 调用者 ⇒ 宿主机上的发布步骤（以及 `upload-artifact`）天然可写；
- 容器用户没有自己的可写家目录，所以 `HOME` 与 npm 缓存都指到工作区内的 `.container-home`
  （prepare 步骤创建，`.gitignore` 已忽略）；
- `RISCV_DOCKER_USER` 作为逃生口：需要特定 uid 映射时覆盖即可。

## 4. 验证（沙箱无法切 uid，于是用 RISCV_DOCKER_USER 反过来模拟 runner 的非 root 步骤）

| 场景 | 结果 |
|---|---|
| 旧行为：容器 root 建 `src/`（属主 0），再以 uid 1001 发布 | 复现 `EACCES: permission denied, open 'src/package.json'`，与线上报错一致 |
| 新行为：容器以 uid 1001 建 `src/`，跑完整 L1 | fetch/build/test 全绿；`src/package.json`、`prebuilds/linux-riscv64/bufferutil.node`、`node_modules` 属主均为 1001 |
| 同上再跑发布（本地 verdaccio + token） | `[publish] wrote src/package.json (generate)` → `+ @ruyisdk/bufferutil@4.2.0` → `publish finished` |

默认（uid 0）路径回归通过；L0 51 个用例通过，golden 已按新模板刷新。

## 5. 教训

容器步骤与宿主机步骤共用同一个工作区时，「谁写文件」必须一起设计——不能只保证功能正确，
还要保证**属主**正确。这条纪律写进了 `docs/recipe-spec.md`（Container user 一节）。
