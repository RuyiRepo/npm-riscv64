## 1. 做了什么

模拟流水线**一行未改**（除发布步骤多写一份报告）。新增一条独立的、事后运行的第二层：

| 层 | 触发 | 机器 | 做什么 |
| --- | --- | --- | --- |
| 构建层（原有） | push / PR | riscv64 容器（qemu） | fetch/patch/build/test/publish |
| 硬件层（新增） | build 成功后 / 手动 | 真机 runner，**不跑容器** | install + verify，然后出报告 |

新增文件：

* `.github/templates/physical.template.yml` —— 第二模板，只有一个步骤，跑 `steps/physical.sh`；
* `.github/workflows/verify-physical.yml` —— `workflow_run`（仅 builds 成功）+ `workflow_dispatch`，
  下载 build 产出的三样东西 → 合并成 plan → 逐目录跑 `physical.sh` → 摘要 + 上传报告 → 终判；

  任何退出路径都写 `physical-report-<slug>.json`；
* `scripts/install_template.sh` —— 生成 `steps/install.sh`：从读仓库 `npm pack` 取 tgz、本地算 sha512 SRI、

* `scripts/auth_function.sh` —— `setup_auth` 从 publish 模板抽成共享文件（发布与物理步骤同一份实现）；
* `scripts/physical_plan.mjs` —— 合并 publish 报告成 plan、打印 job summary 表格、给终判退出码。

  `token`/`basic` 必须给 `token_env`、`source ∈ registry/tarball`）；`verify` 进 ``SNIPPET_NAMES``；

## 2. 为什么这样切

* **不阻塞发布**：真机稀缺，排队绝不能卡住交付；所以是 `workflow_run` 事后层，构建层不动。
* **验的是"发出去的那份"**：硬件上从**读仓库**取 tgz、本地算 sha512，与发布报告里的摘要比。
  不同就是 `digest` 失败——不是重试、不是兜底、不是"环境问题"。
* **兜底只为一个场景存在**：发布报告说 `served: unverified`（registry 收下了但什么都不给可核对），
  这时才用 build 留下的 tgz 装——它仍然要和报告里的摘要一致。若报告里有摘要而机器读不到仓库，
  那是**这台机器的网络/凭据问题**，报 `registry` 失败，绝不用兜底把问题盖过去（D39 的教训）。
* **失败分类即受众**：`environment` 是运维的事（架构/node 版本/磁盘/锁），
  `registry` 是网络与凭据，`digest`/`install`/`execute` 才是产物。混在一起报，等于把机器问题栽给包。
* **不留痕**：runner 是常驻容器，所以 `mktemp` + `trap`、`HOME`/cache/`.npmrc` 全隔离、绝不 `-g`；
  工作流另有 `concurrency: physical-riscv`（不取消）+ 容器内 `flock` + 清扫 6 小时前的残留目录。

## 3. 执行中撞到的四个坑

1. **`sed … | head -1` 在 `pipefail` 下是 SIGPIPE**：`/proc/cpuinfo` 取字段时 sed 还在写、head 已退出，
   整步以 141 结束，事件里看起来"产物坏了"。改成 `awk` + 显式 `exit`。
2. **`require(path.join(pkgDir, 'node-gyp-build'))` 找不到**：npm 会把依赖提升到 consumer 的
   `node_modules/`，不从包目录里。改成 `require.resolve('node-gyp-build', { paths: [pkgDir] })`。
3. **`npm pack --json` 两种形状**：npm ≤10 是数组、≥11 是**以包名为键的对象**。install 步骤已按
   `Object.values(raw)[0]` 读（与发布 helper 同规则）；本地 L2 用镜像里的 npm 9.2.0 走数组、单测走对象。
4. **占位符吃掉了 GitHub 表达式**：渲染器把 `${{ inputs.plan }}` 里的 `{{ inputs.plan }}` 当占位符，
   于是"缺少占位符"报错。修了 `substitute()`：前面是 `$` 的一律放行。

## 4. 复演（无真机）

复演用 `tests/rehearse_physical.py` 一条命令完成（发布 → 渲染物理 action → 合并 plan →
在 riscv64 镜像里跑 `steps/physical.sh` → 打印 verdict 与各项断言）。

三个配方在 `.dsh/tmp/physrun/` 各跑了一遍 verdaccio（4890）→ 渲染发布 → 真发布 → 在
`--platform linux/riscv64` 镜像里跑 `steps/physical.sh`：

| 配方 | 结果 | 关键断言 |
| --- | --- | --- |
| `bufferutil@4.2.0` | `ok`（59 s） | 摘要一致、`prebuilds/linux-riscv64/bufferutil.node` 被 node-gyp-build 解析到、mask/unmask 往返 23 字节、`file` 报 `UCB RISC-V` |
| `utf-8-validate@6.0.6` | `ok` | 摘要一致、5 组校验用例、ELF 为 RISC-V |
| `rolldown@1.3.3` | `ok`（65 s） | 包装层无 `.node`、`@rolldown/binding-linux-riscv64-gnu` 经 `optionalDependencies` 真装、打包产物 `42` 保留、ELF 为 RISC-V |

复演里还撞到一件事，值得记下：手工 `cp -r`（不带 `-p`）会**丢掉可执行位**，
而 npm tar 会把文件模式写进 tarball，于是同一棵树打出的摘要在两次复演里不同
（`prebuilds/linux-riscv64/bufferutil.node` 一处 0755、一处 0644）。这不是发布不确定，
是"复演的树不是真树"——`npm pack` 对同一棵树是确定性的（连续两次打包摘要一致，已实测），
所以复演脚本改用 `shutil.copytree`（保留 mode），vd 里那份错的先 unpublish 再发。

同时验证了三种非 `ok` 路径确实报对：发布版本已被别人占据时 `served: mismatch`（报告照写）；
兜底 tgz 与报告摘要不一致时 `12`；读不到仓库且报告有摘要时 `11` 并明说"这是机器的问题"。
