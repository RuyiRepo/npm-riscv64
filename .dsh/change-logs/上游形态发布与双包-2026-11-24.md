# 上游形态发布与 rolldown 双包（2026-11-24）

## 一、问题

三个配方发布出去的包，和上游发布的不是同一个东西：

| 包 | 上游发布 | 我们此前发布 |
| --- | --- | --- |
| `bufferutil@4.2.0` | 13 个文件，含 6 个平台 prebuild | 8 个文件，只剩 `prebuilds/linux-riscv64` |
| `utf-8-validate@6.0.6` | 16 个文件，6 个平台目录 | 11 个文件，只剩 riscv64 |
| `rolldown@1.3.3` | 58 个文件的纯 JS 包 + 16 个平台包 | 59 个文件，19.5 MB 的 riscv64 二进制塞进 `dist/shared/` |

后果有两种，都不轻：非 riscv64 用户装到的是**缺平台的包**（x64/arm64 只能回落源码编译，macOS/Windows 直接没有二进制）；`rolldown` 则是**每台机器都下载 19.5 MB 的 riscv64 二进制**，x64 用户白付存储与带宽。第二条正是本轮要修正的核心：我们改的是上游的打包习惯，而不是只往包里加东西。

## 二、定案（用户确认的三条原则）

1. **不改上游打包，只加上 riscv64 增量。**
   - prebuild 型包（bufferutil / utf-8-validate）：上游把各平台 prebuild **发在同一个包里** → 我们的发布物 = 上游 tarball + `prebuilds/linux-riscv64`，其余 13/16 个文件逐字节不动。
   - rolldown 型包：上游**发两个包**（主包 + `@rolldown/binding-<arch>-<abi>` 平台包）→ 我们的发布物 = 那对包，绑定 3 个文件、主包 58 个文件只多一条 `optionalDependencies`。
2. **测试走上游自己的套件**，只额外加上 riscv64 专属用例（riscv64 平台上要能被加载、被解析、被打包）。
3. **生成的 patch 是可直接提交给上游的 riscv64 增量**：`upstream/` 里的是 PR 形态，`patches/` 里的是构建期补丁，两者由检查脚本硬隔离。

## 三、实现

### 3.1 渲染器（`scripts/render.py` + `recipe_lib.py` + 新文件）

- `npm_publish[].base`：`kind: source-tree`（默认）| `kind: upstream-tarball`（`url` 必须以 `<name>-<version>.tgz` 结尾 + 必需 `sha512` `integrity`）。
- `overlay`：相对路径列表，只允许**新增**；`allow_overwrite: true` 才允许覆盖上游文件（唯一的覆盖场景是注册表地址）。
- `manifest_shape`：`upstream` | `generated` | `template`（配 `manifest_template`，占位符 `{{name}}/{{version}}/{{registry}}/{{os}}/{{cpu}}/{{libc}}/{{main}}`，残留占位符即报错）。
- `role: binding`（平台包）与 `optional_dependencies`（只允许在 `role: main` 上，且只能引用同一配方里的平台包）。
- `readme`：给平台包准备 README（上游自己也随包发一个）。
- 新文件 `scripts/publish_manifest.mjs`（清单处理）与 `scripts/publish_template.sh`（真实 shell 模板）：写成独立文件而不是 Python 里的字符串，这样 L0 能对它们跑 `node --check` / `bash -n`，也避免三层引号。

关键的架构选择：**上游 tarball 的下载与校验发生在 publish 步骤内**（runner 上，不是容器里）。publish 侧不参与构建 key（§13.11 口径只看渲染后的 fetch/patch/build），所以配方换发布形态、甚至改 integrity 都不会让缓存失效。

### 3.2 配方

- `bufferutil/4.2.0`、`utf-8-validate/6.0.6`：`.stat` 改 upstream-tarball 基座 + overlay，`manifest_shape: upstream`；`commands/test` 改为「上游 mocha 套件 + riscv64 断言」。
- `rolldown/1.3.3`：两条 `npm_publish`（`role: binding` 的 `@rolldown/binding-linux-riscv64-gnu` + `role: main` 的 `rolldown`）；`commands/build` 把绑定 stage 到 `out/binding/` 而不是塞进 wrapper；`commands/test` 改为「打完两个 tarball → 像消费者一样安装 → 跑上游 JS 测试」。
- 三个 `upstream/*.patch` + `.stat` 的 `upstream_increments`（含 `touches` 与 PR 描述）。

### 3.3 测试策略

- bufferutil / utf-8-validate：上游 `test/test.js`（8 / 10 例）在 riscv64 上原样跑通，不需要跳过任何用例；随后加 riscv64 断言（删掉 `node_modules` 与 `build/` 后仍能解析到 `prebuilds/linux-riscv64`、overlay 目录里恰好一个文件）。
- 跳过的机**存在但不装数**：`tests/riscv64-skip.txt` 跟着配方走（`RECIPE_DIR` 由模板导出），条目要写原因；三个配方目前都没有条目。
- rolldown：上游 `tests/behaviors/emit-debug-data/*.test.js`（3 文件 6 例，**实测 16.07s**）。这组用例要 `import.meta.resolve`，所以包必须以**真实依赖**形态被加载（`server.deps.external`），而不是走 runner 的 SSR 变换——这也是消费者看到的形态。

## 五、过程中发现并修掉的两个真 bug

1. **清单合并「必须变大」的判定把重跑变成失败。** `source-tree` 发布时，清单就写在构建树里；第一次发布把 `@rolldown/binding-linux-riscv64-gnu` 写进去后，第二次跑到这里会看到 17 → 17 而失败（`optionalDependencies did not grow`）。改为**加性且幂等**：上游列的平台一个都不许少、只许加本配方发布的包、重跑是 no-op。这条在本地彩排里真实触发了（`d52cdf3` 之后的第一次 L2 重跑）。
2. **模板文件按仓库相对路径读取**，只在「渲染命令恰好从仓库根目录跑」时成立：`run_action_locally.py` 在 sandbox 里渲染时 `packages/rolldown/1.3.3/templates/package.json` 找不到。改为按配方的绝对路径读；同时让本地 runner 把配方目录拷进 sandbox，这样 `RECIPE_DIR=/w/<recipe dir>` 在本地也和 CI 一样能解析。

顺带修正一处与上游不符：平台包清单原本漏了 `files`（npmjs 的**元数据**里看不到它，但上游 tarball 里确有 `files: ["<binary>.node"]`）——补上后与上游 x64 平台包逐项一致。

## 六、已知风险 / 待 L3

- **目标仓库是否接受 `@rolldown` 这个 scope 的发布**，未验证。本地误用 verdaccio 的 token 直连真仓库时得到 `PUT 403`，那是凭据错（该仓库要 HTTP Basic），不能据此判定 scope 策略。L3（fork 真 CI）会用真凭据跑一次，届时若拒绝，退路是 `PUBLISH_SCOPE=ruyirepo` 改写**主包**发布名——但平台包名不能改（loader 按字面量 `require('@rolldown/binding-linux-riscv64-gnu')`），所以必须在仓库侧放行该 scope，否则 rolldown 只能退为「单包 + 塞二进制」的老形态，这与本轮原则冲突。
- 上游套件的 A 档目前只覆盖 `emit-debug-data` 三文件。上游其余测试是 `.test.ts`，需要 `@oxc-node/core`（riscv64 无二进制）与整仓库 devDeps，在 riscv64 上跑不起来；范围取舍记录在 `.dsh/plan.md` D30。
- `bufferutil` / `utf-8-validate` 的上游 tarball 基座依赖 npmjs 可达（publish 时下载并校验 sha512）。断网重发会失败并报 integrity 错误——这是故意的取舍（宁可失败，也不发一个来源不明的包）。

## 七、L3 发现：主包其实没发出去（已修）

fork 的真 CI（真仓库 + 真凭据）里，绑定包 `PUT 201` 成功（9.3 MB，耗时 **148 秒**——这就是
repo 到仓库的真实带宽），主包却停在这一行：

```
npm http fetch GET 200 .../rolldown 932ms (cache miss)
npm error You cannot publish over the previously published versions: 1.3.3.
[publish] already published: rolldown@1.3.3 (the registry refused a second publish; skipped)
```

注意**这一行前面没有任何 PUT**：npm ≥11 在客户端就拒绝了，一个字节都没发。于是仓库继续供上游原版的
`rolldown@1.3.3`（16 条 optionalDependencies，没有 `@rolldown/binding-linux-riscv64-gnu`），
riscv64 消费者安装后依旧拿不到绑定——**绿的一步，发的是错的包**。这正是本轮最该防的失败模式，而我
把「409 = 已发布 = 跳过」当成幂等，等于把「没发出去」写成成功。

### 根因（可复现）

`npm publish` 在 npm ≥11 里有一道**客户端**预检（`node_modules/npm/lib/commands/publish.js`）：

```js
if (!force) {
  const { versions } = await this.#registryVersions(resolved, registry)
  if (versions.includes(manifest.version)) {
    throw new Error(`You cannot publish over the previously published versions: ${manifest.version}.`)
  }
```

本地用 npm 12.2.3 复现（verdaccio 4890，同一个包同一版本）：

| 命令 | 结果 |
| --- | --- |
| `npm publish ...`（不带 force） | `GET 200` → 客户端抛错，**无 PUT** |
| `npm publish ... --force` | `PUT 409`（verdaccio 拒绝覆盖）→ `EPUBLISHCONFLICT` |

真仓库此前探针显示**允许覆盖同版本**（PUT 201），所以只要让 PUT 发出去，主包就能覆盖上游版；
被拦住的从来不是仓库，是我们自己的 npm。

### 修法

1. `npm publish ... --force`：把「要不要覆盖」交给仓库判断。理由写进脚本注释与规格文档——本仓库发的
   本来**就是**上游那个版本 + riscv64 增量，替换它正是全部意义。
2. **发布后回读**：`manifest.mjs --assert-served` 计算「这次会传上去的字节」（`npm pack --dry-run --json`，
   dry-run 与 publish 走同一条打包路径，实测 integrity 与仓库中一致），再读仓库该版本的 `dist.integrity`
   （`npm view <name>@<version> --json`，npm ≥11 的 view 用 `preferOnline`，不会拿到发布前的缓存）：
   - 相同且服务端清单仍引用本配方的平台包 → `already published: ... (identical artifact, nothing to do)`，绿；
   - 不同 → **硬失败**并打印两个摘要 + 「开启 redeploy / 删掉该版本 / 换版本」的处置建议。
   于是「绿」的定义从「上传返回成功」改成「仓库确实在供我们的字节」。
3. 顺带确认 npm ≥11 的清单自动订正只是把 `bin` 的 `./bin/cli.mjs` 规范成 `bin/cli.mjs`
   （`pkgJson.fix` 的提示措辞像删除，实际是重写，值仍在），`files` 字段也原样保留——与上游发布物无实质差异。

### 验证

- 新增 `tests/test_publish_assert.py`（6 例，PATH 上放桩 npm）：摘要相同 / `npm ≥11` 的 object 形 pack 输出 /
   摘要不同（两份摘要都出现在报错里）/ 缺平台包条目 / 条目齐全 / 仓库答复不可读 → 判失败。
- L0 **142 用例通过**；`--check-all` 3 配方 0 失败。
- 本地 L2 复跑（npm 9.2.0，verdaccio 拒绝覆盖）：
  - 原树 → `PUT 409` → 回读一致 → `identical artifact, nothing to do`，绿；
  - 改一个字节再跑 → `PUT 409` → 回读不一致 → 步骤失败（`L1 result: FAILED`），报错含两个摘要。

## 八、发布侧改动不触发任何构建（已修）：publish key 与只发布模式

修完上面那条之后，L3 又暴露出第二层问题：**发布脚本改了，但没有任何作业会运行**。

```
# global build input changed: scripts/publish_manifest.mjs
# global build input changed: scripts/publish_template.sh
# bufferutil@4.2.0: build inputs unchanged (key bb563c29406f), skipping
# rolldown@1.3.3: build inputs unchanged (key f1792c16f6f7), skipping
# utf-8-validate@6.0.6: build inputs unchanged (key 6416447a76d1), skipping
# event=push changed=11 targets=0 self_check=True
targets=[]  has_targets=false  publish=false
```

这是构建 key 口径的**设计后果**（build key 有意只看 fetch/patch/build，发布侧改动不影响产物），
但它和「发布步骤本身就是交付物」撞在一起：产物没变 → 无 target → `has_targets=false` → build 作业整体
跳过 → 连 publish 也一起跳过。于是刚修好的发布逻辑永远送不出去。这正是我上一轮还夸过的「发布侧改动零成本」
在另一侧变成了「发布侧改动零效果」。

### 修法：两个 key，三种 mode

1. `scripts/build_key.py` 新增 `publish_key()` + `--publish-key`：只哈希**发布侧**——渲染后的
   publish 步骤 `run:`、`steps/publish.sh`（其中已内嵌解析后的发布规格：仓库地址、平台包、清单模板）、
   以及逐字节复制进 steps 的 `scripts/publish_manifest.mjs`。helper 从「被 key 的那棵树」读取
   （对 base 与 head 各自成立）。
2. `scripts/detect_targets.py` 对每个候选同时比较两个 key，得到三种 mode：
   | build key | publish key | mode | 行为 |
   | --- | --- | --- | --- |
   | 变化 | 任意 | `build` | fetch/patch/build/test/publish |
   | 不变 | 变化 | `publish` | 恢复缓存树，只发布 |
   | 不变 | 不变 | — | 跳过 |
   `merge()` 中同一配方 build 优先（build 模式本来就包含发布）。
3. `publish` 目标只在允许发布时存在（push 到 main，或显式 `workflow_dispatch` + `republish`）；
   PR 里只改发布侧 → 什么都不跑（也没东西可发）。
4. 新增手动杠杆：`workflow_dispatch` 的 `republish` 输入 → 全部配方变成 `publish` 目标，
   **不重建**，从缓存树重新交付。这正是当下需要的动作。
5. action 新增 `publish_only` 输入：跳过 test；并在 publish 前加一道守卫步骤——
   `publish_only && !reuse` 直接失败（拿没恢复过的树去发布 = 发错包）。

## 九、201 之后"校验立刻说仓库里不是我们的字节"（已修）：npm 12 的 `view --json` 是数组

你给的两次 L3 日志都是同一个现象：`npm http fetch PUT 201`、`published`，紧接着断言
`the registry does not serve this artifact: ... it serves: (no integrity)`。

先确认时间顺序：校验确实在 201 之后**同一步、无延迟无重试**地执行（`publish_pkg()` 里
`npm publish` 成功分支之后就是 `manifest.mjs --assert-served`）。所以问题不是"太早读、仓库还没反应过来"。

### 定位

断言读仓库那一半是这样写的：

```js
const theirs = servedManifest();            // npm view <name>@<ver> --json
const served = theirs.manifest || {};
const servedIntegrity = (served.dist || {}).integrity || "";
```

实测同一个 verdaccio、同一个包：

| npm | `npm view pkg@ver --json` 顶层类型 | `dist` 能否取到 |
| --- | --- | --- |
| 9.2.0 | object | 能 |
| 11.21.3 | object | 能 |
| **12.2.3** | **一元素数组 `[{…}]`** | 不能（数组没有 `.dist`） |

npm 12 把 view 的输出改成了"可查询列表"，元素里 `dist` / `optionalDependencies` 都在。
我们把顶层数组当 manifest → `.dist` 为 undefined → 打印 `(no integrity)` → 又把"没读到"
当成"不一样" → 输出"仓库里是别的东西、请开 redeploy"的指控。**红的那一步是误报。**

用桩 npm 复现（integrity 值完全相同）：

```
npm 9 shape (object): PASS   the registry serves this artifact (sha512-qNzgZ5E8cusO...)
npm >=11 shape (array): FAIL  ... it serves: (no integrity) ... that version holds something else ...
```

与你日志逐字一致。runner 上 `npm warn using --force Recommended protections disabled.` 这条
在 npm 11 与 12 都有，但数组形状只在 12 出现，所以 CI 的 npm 是 **12**；本机 L2 用 9.2.0，
所以本地永远绿——这是这次"本地绿、CI 红"的全部原因。

### 你补的那条验证信息改变了结论

你跑的 `npm view bufferutil@4.2.0 --json --registry .../npm-rv-test-group | jq '{dist, optionalDependencies}'`
返回 `dist: { tarball }`（**既没有 integrity 也没有 shasum**）。也就是说：即使把形状修对，
这家私仓的版本文档也不提供任何摘要。于是"校验"必须能退到第三条路：**下载 tarball 自算哈希**。

### 修法（三层证据 + 三态结论）

1. 形状归一：`Array.isArray(parsed) ? parsed[0] : parsed`（npm ≤11 对象 / ≥12 数组都认）。
2. 证据降级：`dist.integrity`（sha512）→ 缺则 `dist.shasum`（sha1）→ 都没有则下载
   `dist.tarball` 自算 sha512 比对。下载用 npm 的凭据规则（按 nerf-dart 最长前缀匹配
   `NPM_CONFIG_USERCONFIG` 里的 `//host/path/:_authToken|_auth`），因为私仓读 tarball 也要认证。
3. 三态而不是两态：**一致** / **确凿不一致**（失败并打印两份摘要）/ **无法验证**。
   无法验证的含义取决于上传：
   - 201 接受后无法验证 → `WARNING: ... was accepted but not verified`，**不判红**
     （包确实在，只是仓库不给摘要、且 tarball 读不到；把它判红等于让这家私仓永远发不出去）；
   - 被拒后无法验证 → **失败**（此时没有任何证据表明消费者拿到的是我们的字节，
     这正是这条检查存在的理由）。shell 侧用 `--accepted` 把这两种情况区分开。
4. 两个闸门：`PUBLISH_VERIFY=digest` 表示只认摘要、不下载（慢链路可选，日志会如实说没验证）；
   `PUBLISH_VERIFY_MAX_BYTES`（默认 64 MB）限制下载体积。
5. 顺带修掉两个会让这条检查"看起来通过但其实没读"的隐患：`dir` 参数改为绝对化
   （`npm pack` 以该目录为 cwd，相对路径会解析成自己套自己）；`unverifiable()` 集中一处，
   避免三处各写一遍措辞。

### 验证

- L0：`tests/test_publish_assert.py` 从 6 例扩到 19 例，新增：npm 12 数组形状（一致→过、
  不一致→失败）、只给 shasum（一致→过、不一致→失败）、只给 tarball（起本地 HTTP 服务，
  真下载真比对：一致→过、被篡改→失败）、tarball 需要 token（证明凭据查找生效）、
  超过体积上限、201 后无法验证→WARNING 且不红、被拒后无法验证→失败、`PUBLISH_VERIFY=digest`
  不发起下载。全量 **165 用例绿**。
- 端到端演练（用 verdaccio 里真实发布的 bufferutil tarball 当"仓库里的字节"）：
  起一个与私仓同形的替身（元数据剥掉 integrity/shasum，只留 tarball）：
  - 一致 → `the registry serves this artifact (tarball sha512 ..., 169493 bytes)`、exit 0；
  - 把包目录加一个文件 → `the downloaded tarball differs (169493 bytes, sha1 ...)` + 两份 sha512、exit 1；

  "name mismatch" 措辞已改），并让它支持 `DSH_L2_PORT`（默认端口被占用时可用）。L2 全绿。

## 十、binding 发布超时：npm 的 `fetch-timeout` 是整个请求（含上传）的预算

L3 这次红的是 `@rolldown/binding-linux-riscv64-gnu`：三次 `attempt X failed with FETCH_ERROR`，
最后 `network timeout at: …/@rolldown%2fbinding-linux-riscv64-gnu`，而私仓日志里看不到请求。

先回答"是不是又是 npm 客户端版本不兼容"：**不是**。

- `minipass-fetch` 的 `request.timeout` 是**一个墙钟定时器**，从 socket 分配时启动，
  覆盖"上传 + 等响应"整个过程；npm 11 的 `minipass-fetch@5` 与 npm 12 的 `@6` 里这段代码
  **逐行相同**，npm 9/11/12 的 `fetch-timeout` 默认值也都是 5 分钟。
- 本机对同一个慢速 registry（每秒只收 400 kB）用同一个 9.3 MB binding 包实测：
  npm 12 `--fetch-timeout 20000` → 23 s 后 `network timeout at …`，body 未传完；
  npm 11 同样参数 → 23 s 后同一句错误；两者 `content-length` 12172857/12172858（差 1 字节）。
  npm 12 `--fetch-timeout 200000` → 34 s 后 `+ @rolldown/…@1.3.3` 成功。
  即：**同样的包、同样的仓库，只是预算不同，结果就不同**。

### 为什么现在才炸

- binding 的 tarball 9.3 MB，`npm publish` 把它塞进 `_attachments` 的 base64 JSON 里，
  **请求体 ≈ 12.2 MB**。
- 上次成功的那次上传耗时 148 s（≈84 kB/s），刚好在 5 分钟预算里；这次路由更慢
  （私仓侧还会先缓冲整个请求），300 s 不够，于是 npm 在**上传途中**放弃。
- 放弃发生在 body 未传完时，前面的代理不会把未完成的请求转给私仓——**这就是"私仓日志里请求没到达"**。
- npm 还会重试（默认 `fetch-retries: 2`）：三次尝试各把 12 MB 再传一遍，纯浪费 ~15 分钟。

### 修法：把预算按包体算出来，并显式传给 npm

`scripts/publish_manifest.mjs` 新增 `--plan <spec> <dir>`，在发布**之前**给出：

```
P_PACKED_BYTES=9128369   P_FETCH_TIMEOUT=1099000   P_FETCH_RETRIES=1
```

- `P_FETCH_TIMEOUT = min(1h, 300s + 请求体/16kB每秒×1000)`；请求体 = 包体 × 1.4。
  16 kB/s 是"那条成功路由（84 kB/s）慢 5 倍"的保守假设；普通小包得到 300 s+几十秒，
  binding 得到 18 分钟。
- 包体 ≥ 4 MiB 时 `--fetch-retries 1`（重试要整包重传，两次足够），小包保持 npm 默认。
- `PUBLISH_FETCH_TIMEOUT`（毫秒）可直接覆盖公式（含类型校验，非法值直接失败）。
- publish 步骤新增一行可观测输出：`upload 9128369 bytes, fetch timeout 1099000ms`，
  并把 `--fetch-timeout`（与需要时的 `--fetch-retries`）传给 `npm publish`。

### 验证

- L0 新增 `tests/test_publish_plan.py`（7 例）：普通包 200 kB → 318000 ms 且不改重试；
  binding 9.3 MB → 1099000 ms 且重试降为 1；4 MiB 阈值两侧；1 小时上限；
  覆盖值生效；非法覆盖值失败；pack 失败在发布前就停。`tests/test_render.py` 增一例
  钉住 `--plan`/`--fetch-timeout`/`--fetch-retries`/日志行真的进了脚本。
- 真实渲染步骤跑一遍（verdaccio）：binding 打印 `upload 9128369 bytes, fetch timeout 1099000ms`，
  wrapper 打印 `upload 231845 bytes, fetch timeout 321000ms`，两条都正常走完"拒绝→读回→一致"。
- 慢速 registry 实测（见上）：同一份被控在上传途中的请求，短预算必炸、长预算必成。
