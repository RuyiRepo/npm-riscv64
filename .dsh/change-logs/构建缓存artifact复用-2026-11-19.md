# 构建缓存：artifact 复用落地（D16 / S4 收尾）

日期：2026-11-19
前提：L3 三处故障（镜像缺失、GHCR 403、发布 EACCES）修完后，main 上首跑全线通过。

## 1. 要解决的问题

模板或工具链一改，配方级变更检测就会把相关配方全部重选，于是每条都要重付一次模拟构建
（bufferutil 约 43 s，Rust 包是其数倍）。D16 原设计是「main 侧复用 PR 产物」，但没接线。

## 2. 关键决定：从「定位链」改为「内容寻址」

原设计（plan §5.1）要依次做：合并提交 → `commits/{sha}/pulls` 找 PR head → `gh run list --commit`
找 run → `gh run download` → 再 `git diff pr_head..merge -- packages/ template` 判过期。

改成：把「能改变产物的输入」直接哈希成 key，写进 artifact 名，命中即复用。

理由：
- **命中即等价**，不需要 diff 判过期，也不会在两个 PR 先后合入时误判；
- **覆盖面更广**：直推 main、重跑同一 commit、PR 反复推同一配方都能命中；
- **少两次 API 往返**，也少一类竞态。

key 的输入来自 `scripts/build_key.py`：配方版本目录（`.stat`/`commands/`/`patches/`）、该包的
`common/` 层、`.github/templates/`、`scripts/`、`docker/`、解析后的镜像 ID。可选 `--extra` 预留
渲染期改写。

## 3. 缓存对象是「整棵 src 树」，不是单个产物

一开始想只缓存 `.node`，但那样跑不下去：发布要以 `dir: "."` 打包整棵树，测试要用
`node_modules` 里的 `node-gyp-build` 按消费者方式解析 prebuild。所以缓存单元 = `src/`
（排除 `.git`）。

命中时 action 收到 `reuse: true`，只跳过 `fetch`/`patch`/`build`；**`test` 始终执行**（复用产物也要
校验，含 RISC-V 架构断言），`publish` 语义不变。

## 4. 实现

| 文件 | 改动 |
|---|---|
| `scripts/build_key.py` | 新增：收集输入、内容摘要、12 位 key；`--list` 打印参与哈希的文件 |
| `.github/templates/action.template.yml` | 新增 `reuse` 输入；`fetch`/`patch`/`build` 加 `if: inputs.reuse != 'true'` |
| `.github/workflows/build.yml` | 新增「Compute build key → Restore cached build tree（`continue-on-error`，查不到即回退）→ Pack/Upload build tree（仅在真构建后）」；权限补 `actions: read` |
| `tests/test_build_key.py` | 18 个用例：稳定性、各类输入敏感性、common 层、无关配方不失效、`.pyc` 忽略、真实仓库配方 |
| `tests/run_action_locally.py` | `evaluate_if` 支持多输入；新增 `--reuse` |

artifact 名：`<slug>-<ver>-riscv64-tree-<key12>`（例 `ruyisdk-bufferutil-4.2.0-riscv64-tree-77f1d80d3571`），
保留 90 天。恢复用 `gh run download` + `tar xzf --no-same-owner`（树必须归 runner，而不是打包者）。

## 5. 验证

- L0：70 个用例全通过（原 51 + 新增 18 + 1 个 guard 回归）
- 本地端到端：真构建 `.dsh/tmp/cache-a` → 按工作流方式打包（4.1 MB / 2382 条）→ 恢复到
  `cache-b` → 带 `--reuse` 跑：`fetch`、`build` 均被 `if` 跳过，`test` 执行通过，`publish`
  对着 verdaccio 出版成功（`+ @ruyisdk/bufferutil@4.2.0`）
- L2 发布语义回归通过

## 6. 残余风险

- 缓存里的 `package.json` 可能是上一轮发布写过的（发布在打包前执行）。`generate` 档位会按
  `.stat` 重写、`verify` 档位要求正是该身份，两种档位都自洽；若未来出现「打包后再改 manifest」
  的档位，需要把打包挪到发布之前。
- `.git` 不入缓存，若某配方在 `test` 里读 git 信息会失效；当前无此用法，规则写进 spec。
