## 3. 由 D18 推出的三条设计约束（需求未明说，但缺了会出错）

### 3.1 发布顺序必须是 A → B，而不是反过来

若先发 B：在 B 已可见而 A 尚不存在的窗口里，`npm install B` 会在解析 `optionalDependencies` 时退化（拿不到 riscv64 那一项）。**先发 A 能保证「B 一旦可见就一定能装」。** 这条已写进 §6.4 与风险 R-h。

### 3.2 发布前必须做 A↔B 交叉校验

B 的 patch 往 `optionalDependencies` 里加的一行指向 A 的某个版本 —— 这行是**手写进 patch 的**，而 A 的版本写在 `.stat` 里。两个真相源必然漂移（改 A 版本忘了改 patch，是很容易发生的事）。因此发布前断言：

```
B.optionalDependencies[A.name] == A.version
```

不一致即失败（R-g）。同理校验 A 自身 `package.json` 的 `name`/`version` 与 `.stat` 一致，以及 A 的产物经 `file` 断言确为 RISC-V（防止把 x86 产物发成 riscv64 包）。

### 3.3 「patch 新增 A 包」意味着 patch 必须是可创建文件的

A 包通常在上游不存在，是**由 patch 从无到有**创建的（目录 + `package.json` + 产物拷贝逻辑）。`git apply` 支持新增文件，但要求 patch 用 `new file mode` 的标准格式（`git diff --no-index` / `git format-patch` 产出即可）。这条要在 `docs/recipe-spec.md` 里明写，否则配方作者用普通的 `diff -u` 生成补丁会在 CI 里失败。

## 4. 幂等与重入（由「可能发两个包」放大）

单包时代幂等只是「别重复发」；双包时代它变成**故障恢复机制**：A 发成功、B 校验失败 → 重跑时 A 命中等同跳过、只补 B。所以：

- 幂等检查（`npm view <name>@<version>`）不是优化项，是**必须**。
- 发布步骤的失败不可「回滚」（npm 不支持 unpublish 的可靠语义），只能靠幂等 + 重入收敛。
