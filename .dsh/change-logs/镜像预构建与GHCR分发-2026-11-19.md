# 镜像预构建与 GHCR 分发（L3 首跑修正）

日期：2026-11-19
触发：L3 首跑在 `Run composite action` 的 `prepare riscv64 emulation` 步骤失败。

## 1. 现象

```
prepare riscv64 emulation
riscv image: npm-riscv64/toolchain:riscv64
Unable to find image 'npm-riscv64/toolchain:riscv64' locally
docker: Error response from daemon: pull access denied for npm-riscv64/toolchain
Error: Process completed with exit code 125.
```

同一 job 里前一步 `Build riscv64 toolchain image` 返回 0，却没有留下镜像。

## 2. 原因判断

`docker build`（buildx）默认把结果留在**构建缓存**里：显式 `--platform` 而不给
`--load`/`--push` 时，步骤照样退出 0，但本地镜像库里什么都没有。于是下一步
`docker run` 找不到镜像、转而去 Docker Hub 拉一个根本不存在的仓库名，报出
"pull access denied" 这种与真实原因无关的错误。

结论：**在流水线里现建镜像这条路本身就不可靠**，而且代价高——本机实测在
riscv64 模拟下 apt 装 build-essential/nodejs/npm 约十分钟，每个矩阵 job 都要付一遍。

## 3. 改法（采纳你的提议：本地/一次性构建 + 提前推送）

1. 新增 `.github/workflows/toolchain-image.yml`（`workflow_dispatch`）：`buildx build
   --platform linux/riscv64 --push` 推到 `ghcr.io/<owner>/npm-riscv64-toolchain`，
   同时打 `:riscv64`（滑动）和 `:sha-<12位>`（可钉）两个标签。`--push` 是让结果离开
   构建缓存的动作，缺了它就会重演同一故障。
2. `build.yml` 删掉现建镜像的步骤，改为：解析镜像名 → 登录 GHCR → `docker pull` →
   `docker image inspect` 回读镜像 ID。镜像名优先取仓库变量 `RISCV_IMAGE`，否则用
   `ghcr.io/<小写 owner>/npm-riscv64-toolchain:riscv64`（GHCR 拒绝大写仓库名）。
3. action 模板的 `prepare` 步骤改成「本地没有就拉」：先 `docker image inspect`，缺失时
   `docker pull`，仍失败则打印「设 RISCV_IMAGE 或本地构建」的可执行提示再退出。这样本地
   L1 与 CI 走同一条路径，且失败信息直接指向动作而不是 Docker Hub 的假象。

## 4. 验证

- 起本地 registry(`registry:2` @127.0.0.1:5000)，推入工具链镜像后**删掉所有本地标签**，
  再跑 L1：`prepare` 步骤打印 `Status: Downloaded newer image`，容器内 `uname -m` = `riscv64`。
- 用这个「拉来的镜像」跑完整 L1（fetch/build/test）通过。
- L0 51 个用例全通过（golden 已按新模板刷新）。

## 5. 遗留

- GHCR 包默认私有；`build.yml` 里带 GHCR 登录，私有也能拉。若要匿名可拉，需要把包
  可见性改成 public。
- 改了 Dockerfile 之后必须重跑 `toolchain-image` 工作流（或本地 `push` 同名标签），
  否则 CI 继续用旧镜像。后续可以考虑「Dockerfile 变更自动触发重建」。

## 6. 第二处修正：GHCR 403 Forbidden

推完镜像后 CI 的 `Pull toolchain image` 报：

```
failed to resolve reference "ghcr.io/cannedfish/npm-riscv64-toolchain:riscv64":
unexpected status from HEAD request ... 403 Forbidden
```

但在本机**匿名** `docker pull` 同一 tag 成功，说明镜像其实是 public。

原因不是可见性，而是 CI 里那次多余的登录：`docker/login-action` 用 `github.actor` +
`GITHUB_TOKEN` 登录 ghcr.io，而该 token 对「本地用 PAT 推进用户命名空间的包」没有读权限；
Docker 一旦为某 registry 持有凭据就**不会**回退匿名，于是带着无效 token 拿到 403。

改法：登录改成**有 token 才登录**。只有仓库 secret `GHCR_TOKEN`（PAT，`read:packages`）存在时
才 `docker login`，否则明确打印「匿名拉取（公开镜像可用）」直接继续；`docker pull` 失败时按
「公开包查 tag / 私有包连接仓库或加 GHCR_TOKEN」给出两条可执行提示。

顺带修正一个判断：上一节写「GHCR 包默认私有」并不适用于本场景——本地 push 的包可以是公开的，
真正的坑是「带错凭据」，不是「默认私有」。
