## 1. Q-f 定案（D25：包名即身份）

**结论**：update 模式下，清单 `name` 与 `.stat` 不一致 → **直接失败**，不覆盖、不补齐、不跳过。

需求方给出的理由比「防事故」更根本：

> 如果不一致，我们的包就不叫更新，而是新发了 —— 这与「让开发者能够无感获取到 riscv64 支持」的原则相悖。

这条理由把 `name` 和 `version` 的性质区分开了，草案已按此写明：

| 字段 | 性质 | 处理 |
|---|---|---|
| `name` | **身份**（决定「是不是同一个包」） | 必须与 `.stat` 一致；不一致 = 失败 |
| `version` | **本次构建的目标版本**（不是身份） | 由 `.stat` 决定并**写入** |

改名的后果被明确记进 §3.3：原包使用者依然拿不到 riscv64 支持，同时还多出一个无人引用的孤儿包 —— 双输。

## 2. 新增 §12「测试与验证策略」

### 2.1 为什么分四层

这个项目有相当一部分正确性只能在真实环境里暴露（托管 runner 的 qemu 是否就绪、scoped 名能否做 artifact 名、artifact 能否跨 run 复用），但**也有一大半完全可以在本机闭环**。把两者混在一起会导致「等环境」阻塞一切，所以拆成 L0–L3：

| 层 | 覆盖 | 环境 | 阻塞于环境申请？ |
|---|---|---|---|
| L0 静态与单元 | 渲染器、detect、生成片段语法 | 本机 Python + git | 否 |
| L1 片段真实执行 | fetch 降级、patch、build、架构断言 | 本机 docker + qemu | 否 |
| L2 发布语义 | A→B 顺序、幂等、update 不丢字段、漂移拦截、重入 | 本机 verdaccio | 否 |
| L3 真 CI | 7 件事（见 §12.4） | GitHub Actions | **是** |

### 2.2 本机能力实测（本轮新增的客观依据）

不靠假设，直接探了一遍：

| 项 | 结果 |
|---|---|
| docker | ✅ 29.1.3（linux/x86_64） |
| qemu binfmt | ✅ `qemu-riscv64` 已注册（flags `POCF`） |
| riscv64 容器 | ✅ `docker run --platform linux/riscv64 debian:trixie-slim uname -m` → **`riscv64`** |
| 网络 | ✅ npm registry 200、GitHub 可达 |
| jq / node / npm | ✅ 1.8.1 / 22.22.1 / 9.2.0 |
| 缺失 | pytest、gh、shellcheck、act（均非必须） |

**结论：L0–L2 可以在本机闭环，不必等 GitHub。** 这让「先做实现、再谈验证环境」变成「实现与 L0–L2 验证可以并行推进」。

### 2.3 分层设计里两个刻意的选择

1. **L0 用 stdlib `unittest` 而不是 pytest** —— 本机没有 pytest；这个仓库目前只有两个 Python 脚本，为它们引入依赖链不划算。等真需要夹具/参数化再升级。
2. **L1 直接抽 action.yml 里的 `run` 块执行，而不是另写一套测试脚本** —— 被测对象必须是「渲染真正产出的东西」，否则测的是测试脚本自己的逻辑。这也让 L1 顺带验证了 R1（缩进）在真实执行层面的正确性。

### 2.4 L3 的 7 件事必须点名，否则容易自欺

托管 runner 与本地 qemu 不等价。特别提醒一条：本机能跑 riscv64 容器，**不代表** `docker/setup-qemu-action` 在 GitHub 托管 runner 上对 riscv64 就绪（R-a 仍未验证）；本机 x86 CPU + 自有 binfmt 的耗时**也不代表** runner（R-b：6h 上限是否够）。

## 3. 关于「是否需要私有 npm registry」的答复

**不需要**。三层理由：

1. **演练阶段**用本地 verdaccio 即可，零外部维护，且不会误发公共包。
2. **端到端阶段**建议用 **GitHub Packages**（`npm.pkg.github.com`）：仓库自带 registry、鉴权走内置 `GITHUB_TOKEN` + `permissions: packages: write`，不需要额外 secret，scope 天然限定在仓库内。
3. 备选是公共 npm + 测试 scope + granular token（权限限定到该 scope）。

**唯一需要私有 registry 的情形**：发布目标本身就是内部 registry。那时需要它的地址、token、允许发布的 scope 名单。

## 4. 关于「是否需要 GitHub 环境」的答复

**需要，但需求很轻**：

- 一个能跑 Actions 的仓库 —— 建议**临时验证仓或 fork**，别把实验 workflow 直接推到 `RuyiRepo/npm-riscv64`。
- Actions 默认启用即可（无需额外配置）。
- 选 GitHub Packages 时无需 secret；选公共 npm 时给一个 granular token。
- 用来验证 §12.4 那 7 件事，验证通过后再走 PR 合入主仓。
