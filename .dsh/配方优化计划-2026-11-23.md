# 配方改造计划：从"替代式打包"改为"增量式打包"（v2，已采纳讨论意见）

> 状态：**方案已确认，等待最终开工**（本轮仍未改动任何配方/脚本）
> 日期：2026-11-23（v2 依据 2026-11-23 讨论）
> 原三条原则：① 不改上游打包习惯，只做 riscv64 增量（1.1 prebuild 型并进主包、1.2 主包与二进制分离型分两包）；
> ② 测试尽量沿用上游测试，只加 riscv64 用例；③ 生成的 patch 应能作为 riscv64 增量直接向上游提交。
>
> **讨论后新增的两条约束（本版已并入设计）**：
> * **N1 测试只在 riscv64 环境执行**；上游测试里与架构相关（依赖 x64/arm64/darwin/win32 等）的用例**显式绕过**，
>   不允许为了"跑绿"去修改上游测试（那是 patch 污染，违反原则 ③）。
> * **N2 上游增量 patch 不得与 composite action 里的 `patch` 步骤语义冲突**——构建期 patch 与"给上游的 patch"
>   必须分轨、分目录、分校验。

---

## 0. 结论

三个配方从**替代式打包**（把上游发布物改写成我们方便的样子）改为**增量式打包**：

> **以上游已发布的 npm tarball 为基座**，只叠加 riscv64 那一层增量，产物结构与上游**逐字节同构**
> （除了新增的 riscv64 文件/一行 manifest 依赖），并且该增量以"可直接提交上游的 patch"形式留存、受审计。

不再交叉编译其它架构的二进制 —— 其它平台的二进制直接继承上游发布物（用户已确认：效率高、出错概率低）。

## 3. 目标状态

### 3.1 bufferutil 4.2.0 / utf-8-validate 6.0.6 —— 单包，7 平台 prebuild（含上游 6 平台 + riscv64）

```
发布物 = 上游 <name>-<ver>.tgz（逐字节基座）
        + prebuilds/linux-riscv64/<name>.node      ← 唯一增量
```

* bufferutil：13 → **14 文件**，packed ≈ 167 KB，unpacked ≈ 431 KB
* utf-8-validate：16 → **17 文件**，packed ≈ 259 KB，unpacked ≈ 962 KB
* manifest 保持上游原样（`name`/`version`/`install`/`main` 都不动），只把 `publishConfig.registry` 指向目标仓库（recipe 内部行为）
* 客户端：riscv64 用我们编的；darwin-arm64/darwin-x64/linux-x64/linux-arm64/win32-ia32/win32-x64 用上游的（不再现场编译）

### 3.2 rolldown 1.3.3 —— 两包（与上游完全同构）

```
① @rolldown/binding-linux-riscv64-gnu@1.3.3       ← 二进制包（3 文件）
   package.json:
     { name, version: "1.3.3",
       os: ["linux"], cpu: ["riscv64"], libc: ["glibc"],
       main: "rolldown-binding.linux-riscv64-gnu.node",
       engines: "<与上游主包一致>",
       publishConfig: { access: "public", registry: <目标> } }
   + README.md + rolldown-binding.linux-riscv64-gnu.node（19.53 MB）

② rolldown@1.3.3                                  ← 主包 = 上游 wrapper + 一行依赖
   = 上游 rolldown-1.3.3.tgz（58 文件 / packed 227 KB / 0 个 .node）
   + optionalDependencies["@rolldown/binding-linux-riscv64-gnu"] = "1.3.3"
   （不再注入任何 .node；文件数 58 → 59 的唯一原因是 manifest 多了一行？不——见 §4.3：
   仍是 58 文件，manifest 就地改写，不新增文件）
```

* 消费链路（riscv64）：`npm i rolldown`（组仓库）→ 主包 + optional dep（本地优先解析到我们的 1.3.3）
  → 上游 `binding.cjs` 的 riscv64 分支加载 → 完成。**上游源码零改动。**
* 发布顺序：**binding 先、主包后**（`role: binary` + `requires: [rolldown]` 已具备）。
* 其他架构：`optionalDependencies` 其余 16 项照旧从 npmjs 代理解析；主包不含任何二进制。

## 4. 机制改动（渲染器 / `.stat` schema）

### 4.1 新增"发布基座"（核心）

```yaml
npm_publish:
  - role: main
    name: bufferutil
    version: 4.2.0
    registry: https://forgestash-old.verify.oepkgs.net/repository/npm-rv-test-local/
    token_env: NODE_AUTH_TOKEN
    auth: basic
    base:                                   # 新增
      kind: upstream-tarball                # source-tree（旧行为，默认）/ upstream-tarball（新）
      url: https://registry.npmjs.org/bufferutil/-/bufferutil-4.2.0.tgz
      integrity: sha512-…                    # 必填
    overlay:                                # 新增：叠加到基座的增量（相对 fetch 源码树）
      - prebuilds/linux-riscv64            # 目录整体复制；也支持 "src:dst" 单文件映射
```

* `base.kind` 缺省 `source-tree`：完全向后兼容，不改旧配方行为。
* `upstream-tarball` 流程：下载 → 校验 `integrity` 且 `package/package.json` 的 name/version 与 `.stat` 一致
  → 解包 → 按 `overlay` 复制 → `npm publish <dir>`。
* 默认**禁止 overlay 覆盖上游已有文件**（防"悄悄改了上游产物"），需要时显式 `allow_overwrite: true`。
* **只作用于 publish 侧**：`fetch`/`patch`/`build` 是唯一进 build key 的三步；新增 publish 字段不改 build key
  （`fetch` 多拉一个上游 tarball 会让三个 key 变一次 → 缓存失效一次，接受）。

### 4.2 其它字段

| 字段 | 位置 | 说明 |
| --- | --- | --- |
| `libc` | `npm_publish[]` | 写入 manifest 的 `libc`（本 plan 只用 `["glibc"]`）；`os`/`cpu` 已支持 |
| `role: binding` | `npm_publish[]` | `binary` 的别名（上游术语），排序/校验同义 |
| `optional_dependencies` | `npm_publish[]`（main 条目） | 主包要写入 `optionalDependencies` 的包名列表；渲染器从同 `.stat` 其它条目取 version 并校验存在 |
| `manifest_shape: upstream` | `npm_publish[]` | 明确"不重写 name/version，只修正 `publishConfig.registry`"，替代 `generate_manifest` 的双重语义（旧键保留兼容） |

### 4.3 发布脚本改动

* `publish_one` 增加 base 分支；其余优点全部保留：registry URL 规整为结尾 `/`（D30）、`tee` 流式输出 +
  `--loglevel http`（D31）、409/EPUBLISHCONFLICT 分类跳过。
* `optional_dependencies` 由 `MANIFEST_JS` 对**基座 manifest 就地改写**（不新增文件 → 文件数仍 58）。
* 校验：`--check-all` 增加——`base.url` 必须形如 `<name>-<version>.tgz`；`integrity` 必须 sha512；
  `overlay` 路径必须相对、存在且不得与基座文件冲突；`optional_dependencies` 必须在同 `.stat` 有条目且版本一致。

## 5. patch 分轨设计（原则 ③ + 约束 N2：不得与 composite action 的 patch 步骤冲突）

现在有两类"patch"，语义完全不同，**必须分目录、分字段、分校验**：

| | A 类：构建期 patch（已有） | B 类：上游增量 patch（新增） |
| --- | --- | --- |
| 目的 | 改源码让它在 riscv64 上能编译/能过测 | 记录"我们向上游提交了什么"，供 PR 使用 |
| 位置 | `packages/<name>/<ver>/patches/` | `packages/<name>/<ver>/upstream/` |
| 是否应用 | **是**：composite action 的 `apply patches` 步骤在构建容器内 `git apply` | **否**：绝不参与构建，不进入任何 step 脚本 |
| 是否进 build key | 是（patch 渲染进 key） | **否**（纯文档/审计物） |
| 冲突防护 | — | ① 目录名与 `patches/` 不同；② `generate_patch` 只 glob `patches/`（已如此）；③ 新增 L0 测试：生成的 `steps/patch.sh` 中**不得**出现 `upstream/`；④ `--check-all` 校验 `upstream/` 下的 patch 只作为 `upstream_increments` 条目被引用 |

`.stat` 新增：

```yaml
upstream_increments:              # B 类 patch：给上游的增量（不进构建）
  - patch: upstream/riscv64-target.patch
    touches: [packages/rolldown/package.json]     # 审计断言：只改这些上游自有文件
    pr: "add riscv64 to napi.targets so pre-publish emits @rolldown/binding-linux-riscv64-gnu"
```

三份 B 类 patch 的具体形状（**已确认 Q6/Q8：写 patch，且 release 也加**）：

| 包 | patch 内容（上游 PR 形态） | 是否改源码 |
| --- | --- | --- |
| bufferutil | `.github/workflows/ci.yml`：`build` 矩阵加 riscv64 任务（QEMU 或自托管 runner）+ `release` job 加 `tar -cvf <ver>-linux-riscv64.tar`（Q8） | 否 |
| utf-8-validate | 同上 | 否 |
| rolldown | `packages/rolldown/package.json`：`napi.targets` += `"riscv64gc-unknown-linux-gnu"`（Q4：只 gnu） | 否 |

**新增审计 `scripts/check_patches.py`（挂 `render.py --check-patches`，并入 `--check-all`）**：
1. unified diff、`a/`·`b/` 前缀；
2. 路径必须落在 `touches` 声明的上游自有文件上（白名单断言）；
3. 不得出现本仓库路径、配方名、registry、token 等"我们这边"的东西；
4. 在 pin 的 `ref` 干净树上 `git apply --check` 通过；
5. 顶部带 `Upstream-PR:` 说明块（动机/影响/测试方式），可直接摘成 PR 描述；
6. **等价性断言**：B 类 patch 描述的效果必须与我们的发布增量一致 —— 对 rolldown：
   `optionalDependencies` 新增项 == `napi.targets` 新增 target 对应的包名，且 binding 包的 `os`/`cpu`/`libc`/`main`
   与该 target 的 napi 命名规则一致。

## 6. 测试策略（原则 ② + 约束 N1：只跑 riscv64，架构相关用例绕过）

* 所有 `test` 步骤**一律在 riscv64 容器内执行**（`native` 与 `cross` 两种 toolchain 都已如此，不变）。
* 测试 = **上游自带测试命令**（原样调用）+ 少量 riscv64 增量断言；**不修改上游测试文件**。
* 上游用例里若含架构/OS 相关断言（如假定 x64/darwin/win32、或要求现场编译），**显式跳过**并记录理由：
  允许的机制是 mocha/npm 的原生过滤（`--grep`/`--fgrep --invert`、`--ignore`)或一个**独立的跳过清单文件**
  （`tests/riscv64-skip.txt`，一行一条 `用例名  # 理由`），由 test 脚本读取并作为过滤参数；
  跳过的用例必须在 PR/change log 里列名 + 写清"为什么它只对非 riscv64 成立"。

| 包 | 上游测试（riscv64 上跑） | 预期 | riscv64 增量断言 |
| --- | --- | --- | --- |
| bufferutil | `npm test`（mocha） | 秒级 | ① 解开发布产物、删掉 `build/` 后 `require` 必须命中 `prebuilds/linux-riscv64/bufferutil.node`（证明不再靠编译）② 断言**其余 6 个平台 prebuild 目录仍在**（逐个存在+文件非空）③ `file` 断言 RISC-V ELF ④ 产物里不得有 `node_modules/`、`build/` |
| utf-8-validate | `npm test`（mocha） | 秒级 | 同上（上游 6 个 prebuild 文件一个不少） |
| rolldown | **A 档**：`packages/rolldown` 的 JS 测试子集（实测耗时回填本文档） | 待实测 | ① 干净项目从组仓库 `npm i rolldown` → `node_modules/@rolldown/binding-linux-riscv64-gnu/package.json` 存在且 version=1.3.3 ② 主包内**不得**存在 `dist/shared/*.node` ③ 主包 `optionalDependencies` = 上游 16 项 + riscv64 项，16 项一个不少 ④ bundle 冒烟（input→generate→执行） |

L2（verdaccio）端到端：两个包都发布后，在干净 riscv64 容器里装主包 → 断言 optional dep 被解析、binding 被加载、bundle 成功。

## 7. 影响面与迁移

### 7.1 覆盖发布语义（Q2 已实测确认）

目标仓库**支持同版本覆盖**：把 `dsh-probe-slot@0.0.1` 重发一次 → `npm http fetch PUT 201`（不是 409）。
⇒ **"删除重发"等价于"直接重跑发布"**，无需界面上先删版本。

* 影响：`bufferutil@4.2.0` / `utf-8-validate@6.0.6` / `rolldown@1.3.3` 重跑即被新产物覆盖。
* 风险：覆盖是"整包替换"，没有版本回退；因此发布顺序固定 **binding → main**，避免主包先指向不存在的依赖。
* 我们的 409-跳过分类逻辑继续保留（换到真正不允许覆盖的仓库时仍然正确）。

### 7.2 组仓库解析

`@rolldown/binding-linux-riscv64-gnu` 的 1.3.3 只在我们 hosted 仓库里（npmjs 上是 `0.0.0` 占位）。
组仓库必须本地优先（当前即如此），否则 loader 的版本校验会报 mismatch → README 里写明，并在 L2 断言
"解析到的确实是我们的 1.3.3"。

### 7.3 体积（回答"为什么 riscv64 的主包还是 19 MB"）

**主包对所有架构都一样大，都是 ~1 MB；19.5 MB 是二进制，不属于主包。** 我上一版写成"主包 −19 MB"是含混表述，
准确数字如下（MB 为十进制，与 `npm notice` 口径一致）：

| 视角 | 现状（我们当前产物） | 改造后 |
| --- | --- | --- |
| rolldown 主包 | 59 文件；packed **8.93 MB**；unpacked **20.5 MB**（含 19.53 MB 二进制） | 58 文件；packed **227 KB**；unpacked **993 KB**；**零二进制** |
| riscv64 二进制 | 内含在主包里 | 独立包 `@rolldown/binding-linux-riscv64-gnu`：3 文件；unpacked ≈ **19.54 MB**；packed ≈ **8.3 MB**（按上游同平台压缩率折算，实测后回填） |
| **riscv64 客户端** | 下载 **8.93 MB**；磁盘 **20.5 MB** | 下载 227 KB + 8.3 MB ≈ **8.5 MB**；磁盘 993 KB + 19.54 MB ≈ **20.5 MB** → 基本持平 |
| **x64/arm64 客户端** | 下载 8.93 MB（含用不到的 riscv64 二进制）+ 自身 binding 8.86 MB ≈ **17.8 MB**；磁盘 ≈ 41.5 MB | 下载 227 KB + 8.86 MB ≈ **9.1 MB**；磁盘 ≈ 22.0 MB → 省下载 **8.7 MB**、省磁盘 **19.5 MB** |

一句话：**二进制只在 riscv64 机器上出现**；非 riscv64 客户端从此不再为一个自己用不到的 riscv64 二进制付磁盘和带宽。
（bufferutil/utf-8-validate 的体量变化很小：unpacked 21 KB → 431 KB、283 KB → 962 KB，多出来的是**上游其它平台
的 prebuild**，这正是 1.1 要求的"和其它平台一起发布"。）

### 7.4 build key 变化

三份配方的 `fetch` 会新增"取上游 tarball"（进 key）→ 三个 key 全变、缓存失效一次（每包重编 ≈ 3 分钟）。
`.stat` 的 publish 字段（含 `base`/`overlay`/`optional_dependencies`/`upstream_increments`）**不参与 key**。
